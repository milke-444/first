## 点赞并发问题分析：从现象到Lua解决方案

### 一、问题现象

项目采用“首次点赞、再次取消”的Toggle模式。在单用户串行场景下，功能完全正常。

但在**多线程并发测试**中出现数据异常：
- **测试场景**：5个用户、20个线程并发访问同一篇文章
- **预期结果**：点赞数为0（每个用户的点赞和取消操作应相互抵消）
- **实际结果**：点赞数不为0，出现数据残留或计数超出

### 二、错误归因过程

**最初的错误判断**：以为问题源于不同用户之间的并发竞争。但通过分析代码逻辑发现，不同用户操作的是Set集合中的不同用户ID，彼此不存在直接的竞争关系。

**正确的根因定位**：经过深入排查，发现问题**仅发生在同一用户的多线程场景下**。具体原因如下：

1. **代码设计问题**：点赞和取消点赞写在同一个if-else分支中（通过判断用户是否已在Set集合中，决定执行点赞还是取消）。高并发下，同一用户的多个请求可能同时进入同一分支，导致操作次数不均衡。

2. **原子性问题**：点赞功能需要同时操作两个Redis数据结构 一开始并未发现这个隐含问题：
   - `Set`（记录用户是否已点赞）
   - `ZSet`（记录文章的点赞排行榜）
   
   这两个操作不是原子的——`SISMEMBER`判断与`SADD`/`SREM`操作之间存在时间窗口，`SADD`/`SREM`与`ZADD`/`ZREM`之间也存在时间窗口。在高并发下，其他线程可能在这个窗口内修改状态，导致判断条件失效、分支逻辑错误，最终引发数据不一致。

### 三、为什么选择Lua脚本

**核心需求**：记录点赞的Set和记录排行榜的ZSet**必须同步更新、不可分割**。

**方案对比**：

| 方案 | 优点 | 缺点 | 是否采用 |
| :--- | :--- | :--- | :--- |
| **Lua脚本** | Redis单线程执行，天然保证原子性；一次网络往返，性能极高；无死锁风险 | 仅适用于单实例Redis的多命令组合 | ✅ 采用 |
| **分布式锁（Redisson）** | 保证跨系统的资源独占 | 额外网络开销，性能差；需处理锁超时、死锁；复杂场景下才需要 | ❌ 过度设计 |

**选择Lua的理由**：
1. 本项目点赞功能只操作一个Redis实例中的数据，不涉及跨系统竞争，无需分布式锁。
2. Lua脚本将“判断用户状态 + 更新Set + 更新ZSet”封装为一个原子事务，利用Redis单线程特性消除所有竞态窗口。
3. 性能最优：3次Redis命令减少为1次网络请求。
4. 实现简洁：无需处理锁续期、死锁等复杂问题。

### 四、验证结果

- 单用户100线程并发测试：数据完全一致
- 5用户20线程并发测试：数据完全一致
