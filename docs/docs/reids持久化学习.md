## Redis 持久化

### 一、RDB (Redis DataBase)

**是什么**：RDB 是一个经过压缩的二进制快照文件，保存了某个时间点的完整数据库状态。

**优点**：生成与恢复速度快，适合大规模数据的备份与迁移。

**缺点**：如果服务在两次快照之间关闭，会导致该时间窗口内的数据丢失。

**触发方式**：

- **自动触发**：通过在配置文件中配置 `save` 选项（如 `save 60 1000` 表示60秒内至少1000次修改则触发），让 Redis 定期自动执行持久化。其底层会自动调用 `bgsave` 命令来异步生成快照。
- **手动触发**：
  - `save`：会阻塞 Redis 主进程，直到 RDB 文件创建完毕。在此期间，服务器无法处理任何命令请求。
  - `bgsave`：会 fork 出一个子进程在后台生成快照文件，主进程不阻塞，可以继续处理客户端请求。

### 二、AOF (Append Only File)

**是什么**：AOF 是以文本日志的方式，将 Redis 执行的每一条写命令追加到磁盘文件的末尾，是一种基于命令的持久化方式。

**优点**：
- 数据安全性高，丢失数据的风险小。
- 通过备份 AOF 文件，可以恢复误操作的数据。

**缺点**：随着运行时间增长，AOF 文件会变得非常大，占用大量磁盘空间。Redis 提供了 AOF 重写 (`auto-aof-rewrite`) 机制来压缩文件体积。

### 三、混合持久化

混合持久化结合了 RDB 和 AOF 的优点。在 AOF 重写时，会将当前数据以 RDB 二进制格式写入 AOF 文件的开头，之后的写入命令则以 AOF 格式追加到文件末尾。这种方式既保证了数据恢复的高效性，也提升了数据的安全性。

### 四、在我的项目中如何应用？

以我的 **AI 会话功能** 为例：

- **为什么需要持久化**：为了防止项目突然崩溃导致内存中的对话缓存丢失。开启持久化后，即使服务重启，也能恢复上次的对话记录，保证用户体验的连续性。
- **如何区分使用场景**：
  - **Redis 持久化**：适用于需要快速恢复、允许少量丢失的热点数据或临时会话状态。
  - **MySQL 数据库 / 向量数据库**：适用于需要长期保存、结构化查询的核心业务数据。
- **重要补充**：需要分析哪些功能必须依赖持久化，哪些功能可以接受数据丢失（如排行榜缓存），并配合定期清理策略，避免 Redis 内存被无用数据占满。
